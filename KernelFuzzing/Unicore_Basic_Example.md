# Fuzzing A Kernel Module With Unicore

## Building Unicore

```sh
python3 -m venv unicore_venv
source unicore_venv/bin/activate

git clone https://github.com/fgsect/unicorefuzz.git
cd unicorefuzz
```

Patches to AFLplusplus for build to work:

Comment out all of the checks in `check_binary` on line 2070 of **AFLplusplus/src/afl-fuzz-init.c**

Build unicorn support script patch:  
```patch
--- a/unicorn_mode/build_unicorn_support.sh
+++ b/unicorn_mode/build_unicorn_support.sh

-  MYPYTHONPATH=`python -v </dev/null 2>&1 >/dev/null | sed -n -e '/^# \/.*\/os.py/{ s/.*matches //; s/os.py$//; p}'`
+  MYPYTHONPATH=`python2 -v </dev/null 2>&1 >/dev/null | sed -n -e '/^# \/.*\/os.py/{ s/.*matches //; s/os.py$//; p}'`
```

Patch to unicore configspec.py:
```patch
--- a/configspec.py
+++ b/configspec.py

- def init_avatar_target():
+ def init_avatar_target(ucf, avatar):
```

Build with:
```sh
./setup.sh
```

## Kernel Module Fuzzing Example

The very vulnerable kernel module I am using as an example is here: [VulnerableModuleExample](./VulnerableModuleExample/)  

The kernel+rootfs setup I am using is what is described here: [arm32le_versatile_linux2.6_gcc4.6.md](../CrossToolExamples/arm32le_versatile_linux2.6_gcc4.6.md)  

This is going to require three terminal windows, in all of them, source the venv, and then run:
```sh
export PATH=/path/to/unicorefuzz:/path/to/unicorefuzz/AFLplusplus:$PATH
```

I ran the image with the debugger port open but no debugger attached (Qemu `-s` option)  

We need to determine the entry point and the exit point(s) for each fuzzing round. Do this by getting a base address for the kernel module by looking at kallsyms and then figuring out the offsets by looking at Ghidra. In this case, the_vuln_function starts at `0xbf000040` and has one return at `0xbf000098`  

**Note**: I have been doing this testing on 32-bit arm, and for some reason, if I make the exit the `ldmia` (second instruction of return) it misses it, but if I make it the `add sp,sp` (first instruction of return) it works. Not sure why. So, in this case `0xbf000098` is the add instruction, not the ldmia   

For this example, we are assuming that the contents of the buffer, passed as the second parameter to `the_vuln_function` is writeable. So, our goal is to take AFL input of up to 256 bytes and place it in that buffer.  

Based on this information, here is my full `test1_config.py`:
```python
import os

from unicorn import Uc
from unicorn.arm_const import UC_ARM_REG_R0, UC_ARM_REG_R1
from unicorefuzz.unicorefuzz import Unicorefuzz

# A place to put scratch memory to. Non-kernelspace address should be fine.
SCRATCH_ADDR = 0x80000
# How much scratch to add. We don't ask for much. Default should be fine.
SCRATCH_SIZE = 0x1000

# The page size used by the emulator. Optional.
# PAGE_SIZE = 0x1000

ARCH = "arm"
GDB_HOST = "localhost"
GDB_PORT = 1234

GDB_PATH = "gdb-multiarch"

BREAK_ADDR = 0xbf000040

EXITS = [0xbf000098]

# The location used to store data and logs
WORKDIR = "/home/purple/Documents/fuzzing_research/unicore_working_dirs"

# Where AFL input should be read from
AFL_INPUTS = WORKDIR + "/afl_inputs"
# Where AFL output should be placed at
AFL_OUTPUTS =  WORKDIR + "/afl_outputs"

# Optional AFL dictionary
AFL_DICT = None

def init_func(uc, rip):
    pass

def place_input(ucf: Unicorefuzz, uc: Uc, input: bytes) -> None:
    if len(input) > 256:
        os._exit(0)  # too big!

    # Read pointer to input buf:
    r1 = uc.reg_read(UC_ARM_REG_R1)

    ucf.map_page(uc, r1)  # ensure buffer is mapped
    uc.mem_write(r1, input)  # insert afl input
```

With the Qemu VM running, the first step is to attach ucf:
```sh
ucf attach -c ./test1_config.py
```
If succesful, you should see:
```
[+] Breakpoint set at 0xbf000040
[*] Waiting for bp hit...
```

Now, in the Qemu VM, perform the action that will cause the breakpoint to get triggered. In other words, naturally get the VM to the state fuzzing should start at  

You should see:
```
[+] Breakpoint hit! dumping registers and memory
[*] Initial dump complete. Listening for requests from ucf emu.
```

Before actually running with AFL, test a run with just ucf emu by itself. When running with AFL, any exceptions generated by `place_input` will be suppressed, so you will not know if something is wrong unless you run without AFL first:
```sh
cd unicore_working_dirs

# If its first time, you have to mkdir afl_inputs and afl_outputs 

# afl_inputs should contain at least one file that has fuzzing seed material (like "abcd1234")

ucf emu -c ../test1_config.py ./afl_inputs/something
```

The output you should see is:
```
[*] Finished one run (without AFL).
```

If you don't get to that output, something is wrong

Now we run AFL with the emu harness in another terminal window:
```sh
export AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1
export AFL_SKIP_CPUFREQ=1

afl-fuzz -U -m none -i afl_inputs -o afl_outputs -t 60000+ -M master -- ucf emu -c ../test1_config.py @@
```
